## What this is

A background record created automatically when a recurring refill request gets manager-approved for the first
time (see `refill_requests` capability doc). It remembers the pattern (frequency, approval policy) and
auto-generates new refill requests on a schedule, without a human re-typing the same request every week/month.

## The automatic generation cycle

Runs daily (backend cron job). For every active schedule whose `nextRunDate` has arrived:
1. A new refill request is auto-created, copying the item list and approved quantities from the original
   request that spawned this schedule.
2. If the schedule's `approvalPolicy` is `auto_approved`: the new request skips hospital approval entirely,
   starts at `pending_manager_approval`, and a notification goes to the Central Warehouse manager. If no
   warehouse manager is currently assigned to the Central Warehouse department, this notification is silently
   skipped (logged, not sent) — the request still gets created, just nobody gets pinged about it.
3. If `approval_required_each_cycle`: the new request starts fresh at `pending_hospital_approval`, and a
   notification goes to the hospital manager. Same silent-skip behavior if no active hospital manager exists.
4. The schedule's `nextRunDate` advances by its configured interval regardless of whether the notification
   succeeded.

## Cancelling a schedule

Only from `active` status, by anyone with `manage_periodic_refill_schedules`, with a required reason. Once
cancelled, no further requests will be auto-generated from it — but any already-generated requests continue
their normal lifecycle untouched.

## Important: cancelling a schedule does not cancel in-flight requests

If a request was already generated and is sitting in `pending_hospital_approval` when you cancel its parent
schedule, that request is unaffected — it still needs to be individually approved/rejected/cancelled through the
normal refill-request flow.

## Common questions

- **"Why did a refill request appear that nobody created?"** → It was auto-generated by a periodic schedule.
  Check `periodicScheduleId` on the request, or look at the schedules list to find the originating pattern.
- **"I cancelled the schedule but a request is still pending, why?"** → Cancelling only stops *future*
  generation; existing generated requests must be handled individually.
